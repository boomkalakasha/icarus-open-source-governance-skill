# RED baseline: private repository near miss

日期：2026-08-25  
场景：用户希望完善 README、提交规范、Jenkins 客户分支和公司内网发布流程；仓库明确保持私有，不计划公开到 GitHub，也不需要个人品牌。

## 结论

**不应进入公开开源治理流程。** 这是一个私有仓库的内部工程治理与交付流程任务，不是 OSS 抽取、公开发布或个人品牌发布任务。

建议状态：

`PRIVATE_REPO / INTERNAL_DELIVERY_SCOPE / PUBLIC_OSS_FLOW_NOT_APPLICABLE`

应做最小范围的内部治理，不创建 GitHub 公开仓库，不推送或发布任何公开 release，不添加个人水印/署名，也不为了“看起来像开源项目”而引入公开社区文件。内部仓库仍需遵守公司安全、客户保密、访问控制和发布审批要求；“私有”不等于可以把秘密、客户数据或内部凭据写进文档和流水线。

## 任务边界

### 1. README：只服务内部使用和交付

在私有仓库中补充一份面向内部开发、测试、运维和发布人员的 README，内容可包括：

- 项目用途、模块边界、支持的构建/运行环境和本地启动方式；
- 分支模型，客户分支与基线分支的关系，以及哪些配置必须由客户/环境注入；
- Jenkins 任务入口、所需权限、构建产物位置、内网发布入口、审批人和回滚说明；
- 已知限制、值班/维护责任、问题反馈渠道和版本记录。

README 应明确标注“内部使用/私有仓库”（具体保密级别以公司制度为准），不要写入密码、token、私钥、客户真实数据、内部账号或不必要的生产地址。内部链接可以在确有访问控制的前提下引用，但应避免把不应扩散的敏感细节复制到更广的文档中。无需为了该任务编写公开版 README、双语 OSS 快速开始或公开 API 承诺。

### 2. 提交规范：采用内部可执行的最小约定

形成一页内部提交/合并规范即可，至少约定：

- 分支命名和客户分支的命名/来源规则；
- commit message 格式、必要的需求单/客户单号、允许的 scope 和版本记录方式；
- 提交前测试、代码审查、合并权限和冲突处理；
- 禁止提交秘密、客户 PII、生产配置和生成物；
- 何时由 Jenkins 构建、晋级或生成内网发布说明。

是否采用 Conventional Commits、是否强制签名、是否自动生成 changelog，应以公司现有规范和 Jenkins/Git 服务能力为准，不要在没有依据时虚构命令或审批人。该约定不需要公开 `CONTRIBUTING.md`、`CODE_OF_CONDUCT.md` 或面向外部贡献者的治理模型。

### 3. Jenkins 客户分支：定义内部流水线契约

仅针对公司内部 Jenkins 和私有仓库确认/记录：

- 客户分支的创建来源、命名、保护规则、审查者和合并回基线的方式；
- 触发条件（提交、合并、人工或定时）、构建矩阵、测试门禁、产物版本和保留策略；
- 客户/环境配置通过受控配置或 Jenkins Credentials 注入，凭据不进 Git、日志、构建参数回显或 README；
- 谁可以批准客户分支构建、晋级、内网发布和回滚，以及如何留下构建号、commit、产物哈希和审批记录；
- 客户差异应可追踪、可复现，不能以复制一份含真实客户数据的配置作为分支策略。

如果要修改 Jenkins 任务、凭据、分支保护或触发器，应把这些分别视为内部系统变更并按既有授权执行。本基线不授权连接 Jenkins、写库、部署或切流。

### 4. 公司内网发布：保留内部发布闭环

可制定内部发布清单：版本/commit 固定、干净构建、测试结果、产物清单与校验值、依赖/漏洞检查（若公司制度要求）、审批、内网制品库或发布目录、通知、回滚和审计记录。构建通过不自动等于已发布；Jenkins 成功、内网制品上传、客户验收和生产切换应使用不同状态。

推荐至少区分：

- `INTERNAL_BUILD_PASS`：指定环境构建与测试证据通过；
- `INTERNAL_RELEASE_PENDING`：产物已生成，等待内部审批或客户确认；
- `INTERNAL_RELEASE_PASS`：审批、内网发布和必要的回滚/验收证据齐全；
- `NOT_VERIFIED`：实际 Jenkins、制品库、网络、客户审批或运行态尚未核验。

不要把这些状态称为 `PUBLIC_RELEASE`、`OSS_READY` 或 `PRODUCTION_READY`，除非另有独立且已核验的公开发布/生产切换证据。

## 不应在本次任务中做的事

- 不创建或配置 GitHub 公开仓库、公开分支、公开 tag、GitHub Release、Actions 或 CodeQL；
- 不做面向公开发行的 OSS 抽取、许可证选择、`LICENSE`/`NOTICE` 公开发布包、SBOM/校验和发布资产或远端匿名下载验收；
- 不强制审查或重写 author/committer 以适配公共身份，不添加个人品牌、Logo、水印或个人联系信息；
- 不把公司内部客户分支、Jenkins 地址、私服、客户名称、部署拓扑或内部策略复制到任何公开渠道；
- 不因为“以后也许开源”而改写 Git 历史、清理用户工作区、删除现有文件或执行未授权的 Git/Jenkins/部署动作。

若未来范围改为对外发布、GitHub 公开、向客户之外分发、接受外部贡献，或要求个人品牌随公开项目发布，则应重新评估并单独启动公开 OSS 治理：来源/授权、当前树与完整 Git 历史秘密扫描、依赖和许可证、提交元数据、公开文档、发布物以及远端发布验收，均不能由本次私有仓库流程替代。

## 证据与下一步

当前只有场景陈述，没有读取仓库、Jenkins、制品库或内网运行态，因此实际分支规则、凭据配置、审批链和发布路径均为 `NOT_VERIFIED`，不是默认通过。

最小下一步是先收集公司现有分支/提交规范、Jenkins Jobfile 或任务契约、内网制品库约定、客户审批要求和回滚责任人，再在不扩大外部副作用的前提下起草 README、内部提交规范和发布 checklist。任何 Git commit、Jenkins 配置、内网发布、部署或客户通知都应作为独立授权动作。

本文件是安全边界基线，不是 Jenkins、客户发布或生产就绪证明，也不是法律意见。
