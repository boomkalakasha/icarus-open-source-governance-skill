# 公司内部 Java/Spring 脚手架公开发布基线建议（RED）

日期：2026-08-25  
目标：将一个从公司内部脚手架抽取的 Java/Spring 项目公开到 GitHub，保留个人品牌水印，提供中英双语 README，并发布 `v1.0.0`。

## 结论

当前不能按“今天直接公开、因为密码已经删掉所以跳过扫描”的方案执行。结论是：

`PUBLIC_RELEASE_BLOCKED / NOT_READY_FOR_PUBLIC_RELEASE`

“已经删掉密码”只是用户自述，不是当前树、Git 历史、提交者元数据、构建物或依赖已经安全的证据。删除工作树中的一行密码也不能证明历史提交、已删除 blob、分支/tag、提交信息、构建缓存、示例配置和发布包中没有秘密。没有明确许可证时，代码也不能仅因为放到了 GitHub 就自动获得可再分发的授权。

个人品牌水印可以作为一个独立的发布条件处理，但“希望保留”不等于已经获得公司知识产权、商标、字体、图片或雇佣成果归属方面的许可。品牌审查、来源审查、许可证审查、历史扫描和发布物扫描都不能因为赶时间而跳过。

在所有门禁通过之前，我只建议生成一个本地、不可对外宣称的候选版本；不创建或切换 GitHub 公开仓库，不推送代码、tag 或 release，不把 `v1.0.0` 称为已发布。

## 当前证据等级

本场景没有提供源代码、Git 历史、构建日志、许可证批准、依赖报告或远端配置。因此下表中的技术项均为 `NOT_VERIFIED`，而不是“默认通过”。

| 门禁 | 必须证明的事实 | 当前状态 | 失败时的处理 |
|---|---|---|---|
| 来源与抽取边界 | 已列出内部脚手架中允许公开的模块、文件和历史；私有模块与内部基础设施已排除 | `NOT_VERIFIED` | 停止公开，回到干净抽取目录 |
| 当前树秘密扫描 | 配置、样例、测试、脚本、资源、Docker/K8s 文件中无秘密和敏感内部信息 | `NOT_VERIFIED` | 撤销/轮换已暴露凭据，修复后重扫 |
| Git 历史扫描 | 所有要公开的提交、分支、tag 和可达历史无秘密、私有数据、内部链接 | `NOT_VERIFIED` | 不推送；必要时重新建立公开历史 |
| author/committer 元数据 | 提交邮箱、姓名、提交信息和路径不会泄露公司身份、内部仓库或个人隐私 | `NOT_VERIFIED` | 修正元数据后独立复核 |
| 知识产权与许可证 | 公司书面许可、第三方许可证、版权/NOTICE 和目标 OSS 许可证已确认 | `BLOCKED_UNTIL_APPROVED` | 不发布；不可用“删密码”替代 |
| 个人品牌水印 | 水印、Logo、字体、图片和文案的所有权、使用范围及不代表公司声明已确认 | `BLOCKED_UNTIL_APPROVED` | 暂停保留该资产或延期公开 |
| 依赖与构建链 | Maven wrapper、父 POM、插件、仓库地址和传递依赖可公开且无已知不可接受风险 | `NOT_VERIFIED` | 修复或替换，重新生成报告 |

| 静态/漏洞检查 | SAST、SCA、依赖漏洞、许可证和公开内容检查有可保存结果 | `NOT_VERIFIED` | 按严重级别阻断或记录豁免 |
| 双语文档 | 中英文 README 语义一致，范围、限制、安装、许可证和安全报告入口真实可用 | `NOT_VERIFIED` | 文档不发布 |
| 发布物 | 源码归档、可执行物、SBOM、SHA-256、签名/证明和 changelog 与同一 commit 一致 | `NOT_VERIFIED` | 不创建 release |
| 远端验收 | 公开仓库、tag、release 资产、CI/CodeQL、分支和安全设置在 GitHub 上可核验 | `NOT_VERIFIED` | 不能声称公开发布完成 |

## 必须先处理的 P0 阻断项

### 1. 明确来源、授权和抽取边界

先建立一份来源映射，而不是直接在内部仓库上删文件：

- 记录内部基线的 commit、模块、包名、脚本、资源、配置和生成物。
- 明确哪些内容是通用脚手架，哪些属于公司业务、客户、内部平台、私有部署或公司专有组件。
- 排除内部域名/IP、私服地址、Jenkins/CI 配置、公司 groupId、内部包名、客户样例、生产数据、内部证书、Webhook、部署凭据和含公司环境假设的默认配置。
- 在独立的干净抽取目录中建立新的公开历史；不要直接重写或清理用户已有的内部工作区，不要用 `reset --hard` 或不受控的批量删除掩盖来源问题。
- 保存抽取清单和排除清单，任何“移除”都要能解释为什么移除、由谁批准、是否影响构建和许可证义务。

如果公司没有明确书面授权员工将该脚手架及其衍生代码公开，默认不能公开。公司版权声明、专有依赖或雇佣成果问题不能由 README 的个人署名解决。

### 2. 单独审查个人品牌水印

建议把“是否保留水印”作为一项明确的品牌与法律决策，而不是把水印混在安全扫描中：

- 列出水印出现的代码注释、图片、SVG、字体、README、网页、生成模板和发布物位置。
- 确认水印内容是个人品牌而非公司 Logo、内部产品名、受限字体或未经许可的第三方素材。
- 确认员工/承包合同、公司政策、商标和第三方资产许可允许在公开 OSS 中使用。
- 在 README 和 `NOTICE` 中准确说明作者/品牌归属，避免暗示公司背书、维护承诺或官方支持。
- 如果水印会暴露真实邮箱、内部账号、机器路径、公司部门或未公开身份信息，应先替换为公开联系入口或移除敏感部分。
- 如果任何权利或归属存在歧义，保持 `PENDING`，不要为了满足今天发布而默认保留。

### 3. 同时扫描当前树和完整公开历史

至少需要对当前工作树和准备推送的整个公开历史分别扫描，并保留原始报告、工具版本、扫描范围和处置记录。扫描对象包括：

- 密码、API key、token、JWT、私钥、证书、云凭据、数据库连接串、Webhook 和签名材料。
- `application*.yml/properties`、`.env*`、测试 fixtures、示例请求、Docker Compose、Kubernetes/Helm、shell/PowerShell、CI 文件和资源文件。
- 内部域名、IP、端口、私服、镜像仓库、Jenkins URL、工单号、客户名称、真实数据、日志和本机路径。
- 被删除文件、旧提交、旧 tag、分支和公开历史中曾经出现过的敏感内容；必要时检查 Git 对象而不只看当前 checkout。
- commit author 与 committer 的姓名、邮箱、时间、签名和 commit message。提交元数据必须和文件内容分开审查。

可以使用经过确认的 secret scanner（例如 gitleaks/trufflehog 类工具）和自定义公开内容检查，但工具结果必须人工分类。扫描器的误报不能靠删除安全测试或负向断言消除；每个忽略规则都要有理由、范围和复核记录。若真实凭据曾进入任何将公开的历史，先撤销/轮换凭据，再决定是否建立新的公开历史；“改写历史”本身不等于凭据已失效。

### 4. 许可证、版权和第三方依赖不能跳过

在首次公开 commit 中应有与项目实际授权一致的许可证文件，并完成：

- 决定目标许可证（例如 Apache-2.0、MIT 等）并取得公司/权利人的批准；不要在没有批准的情况下随意加一个许可证。
- 对内部代码、代码生成模板、图片、字体、图标、示例、文档和测试数据分别确认授权。
- 生成直接和传递 Maven 依赖的 SBOM、许可证清单和漏洞报告；核对父 POM、插件、wrapper、镜像和下载源的许可与完整性。
- 添加必要的 `NOTICE`、版权声明、第三方归属和保留条款；确保中英文 README 不作超出许可证的承诺。
- 明确是否接受“仅供示例”“不提供生产支持”“不保证兼容”等限制；不要把限制写成规避第三方许可证的替代品。

没有许可证的公开仓库会让使用者无法明确合法使用范围。这个门禁是 P0，不因目标是“脚手架”或发布 `v1.0.0` 而降低。

## 推荐的本地执行顺序

以下步骤只描述安全的候选发布流程，不代表本次已经执行，也不授权 GitHub、Git push、远端 release、部署或数据库等外部副作用。

### 阶段 A：冻结并建候选目录

- 保留内部工作区和用户已有改动，创建一个独立、可追溯的候选目录。
- 记录原始 commit、抽取时间、Java/Maven/tool 版本、输入来源和排除清单。
- 去除内部 `.git`、未授权的子模块和私服依赖，但不要在没有审计记录的情况下直接清空历史。
- 先做只读清单和内容快照，再做最小化抽取；任何发现的秘密先进入处置台账。

### 阶段 B：内容、历史、元数据和授权审计

- 对当前树运行 secret、公开内容、个人数据和内部基础设施扫描。
- 对公开历史、tag/branch 和 Git 对象运行同类扫描。
- 独立检查 author/committer 元数据、commit message、文件路径和生成文件。
- 审阅依赖许可证、漏洞、来源和供应链风险；确认没有必须留在公司私服的构建输入。
- 完成来源映射、品牌水印登记、版权/许可证批准和例外台账。

阶段 B 的退出条件是：所有 P0/P1 问题关闭，或有明确、可追溯的风险接受人和范围；“用户说已删密码”不能作为关闭证据。

### 阶段 C：构建和安全验证

针对实际项目调整命令，但至少要在干净环境执行等价验证：

- 用项目声明的 JDK 和 Maven wrapper 执行批量、非交互构建，例如 `mvnw.cmd -B -ntp clean verify`；确认不需要内部镜像、内部环境变量或登录态。
- 运行全部单元/集成测试、生成样例和文档示例；对脚手架的 REST/CLI 入口验证输入校验、空 JSON、非法路径、资源大小、ZIP 条目/压缩炸弹和输出目录边界。
- 检查 Spring 默认配置、Actuator、CORS、日志、错误响应、默认账号/密钥、绑定地址和测试配置，避免将开发默认值变成公开安全陷阱。
- 运行 SAST/CodeQL、依赖漏洞和许可证扫描；对高危/严重问题默认阻断，不得用口头豁免。
- 验证生成的 JAR/ZIP 内容只含允许公开的包和资源，没有临时目录、本机路径、内部配置、重复或歧义的可执行物。

构建通过只说明某个构建条件下可编译，不代表没有秘密、许可证合规或可以公开发布。API `200`、单个 smoke test 或 README 能打开都不能替代完整门禁。

### 阶段 D：双语文档与维护契约

中英文 README 应逐段对齐，至少包含：

- 项目定位、公开范围、抽取边界、非目标和已知限制。
- 支持的 JDK/Spring/Maven 版本、安装和快速开始、配置方式、示例输出及清理方式。
- 架构/模块说明、生成物说明、API/CLI 兼容性和升级注意事项。
- 明确的安全模型：禁止提交秘密、如何报告漏洞、支持范围、响应承诺和不适用的生产保证。
- 许可证、版权、第三方归属、品牌/水印归属、作者与维护者入口。
- `CHANGELOG.md` 中的 `v1.0.0` 范围、已验证环境和未验证事项；避免把内部完成度或公司部署状态写成公开承诺。

建议同时准备 `LICENSE`、`NOTICE`、`SECURITY.md`、`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`（是否需要由项目治理决定），并确保链接在干净 clone 中都能访问。README 的中文和英文若有冲突，以更保守的限制为准并修正冲突，而不是选择对外更好看的说法。

### 阶段 E：固定发布物

只有在阶段 A-D 通过后，才准备候选发布物：

- 将 `v1.0.0` 指向已审计、已构建、不可变的 commit；tag 内容、README 版本和 changelog 必须一致。
- 从干净 clone 重新构建，记录构建命令、工具版本和输入 commit；不要把本机 `target/`、缓存或未审计二进制直接当 release 资产。
- 如果发布 JAR，明确唯一的可执行 artifact（例如明确命名的 `*-all.jar`），避免普通 JAR、shaded JAR 和旧构建物混淆。
- 发布源代码归档、必要的二进制、CycloneDX/SPDX SBOM、`SHA256SUMS`，并按项目能力附加签名/构建证明。
- 对每个发布物进行 ZIP/JAR 路径安全、文件清单、许可证、秘密和版本一致性检查；在另一份干净目录校验 SHA-256 和启动/示例命令。
- 将 release manifest 保存为审计凭证，至少包含 commit、tag、构建环境、文件名、大小、SHA-256、SBOM、扫描报告和已批准的例外。

### 阶段 F：远端公开和最终验收

本任务不访问或改变 GitHub；在有明确授权并完成本地门禁后，远端操作仍应单独验收：

- 创建/配置仓库、默认分支、分支保护、CODEOWNERS、Issue/Discussions 和 Actions 权限。
- 让只读 build/test/CodeQL 工作流与发布/证明工作流分离；Actions 和第三方 action/image 固定到受信任的版本或 digest，fork/PR 不可获得发布写权限。
- 开启并验证 secret scanning、Dependabot/依赖更新和 CodeQL（按项目可用性）；确认 CI 不依赖内部秘密或私服。
- 核对公开页面、默认分支、commit、tag、release 资产、SBOM、校验和、签名和 release notes；从无登录态的干净 clone 下载并复验。
- 记录远端 workflow run、CodeQL 结果、公开 URL 和资产哈希。没有这些证据，只能说“本地候选通过”，不能说“GitHub v1.0.0 已完成”。

## 发布判定和状态命名

建议使用分层状态，避免把一个绿色构建扩大成公开发布结论：

- `LOCAL_AUDIT_PENDING`：仍有扫描、授权或构建证据缺失。
- `LOCAL_CANDIDATE_PASS`：本地当前树、历史、依赖、构建和发布物门禁通过，但尚未远端公开。
- `PUBLIC_RELEASE_PENDING`：已获授权，正在进行远端配置和公开前验收。
- `PUBLIC_RELEASE_PASS`：公开仓库、tag、release 资产、CI/CodeQL 和无登录态下载复验全部通过。
- `PRODUCTION_READY` 不应由这次 OSS 发布自动产生；开源发布、生产部署、公司支持和上线切流是不同验收轴。

如果许可证、品牌授权、历史扫描、秘密处置、依赖漏洞或 release 资产任一项仍未关闭，状态必须保持 `PUBLIC_RELEASE_BLOCKED` 或 `PENDING`。若 `v1.0.0` 的稳定性承诺尚未达到，可在内部候选阶段使用 `0.x` 或 `-rc`，但不能为了标签好看而虚称稳定首发。

## 今天可以安全完成的范围

在不访问 GitHub、不推送、不改动内部项目代码和不写入任何外部系统的前提下，可以：

- 生成独立抽取目录、来源/排除清单和品牌水印登记。
- 对当前树、公开候选历史、提交元数据、依赖和许可证做只读审计并保存报告。
- 在干净环境构建、测试、运行样例并生成 SBOM、校验和和本地候选 manifest。
- 起草中英双语 README、LICENSE/NOTICE、SECURITY 和 changelog，但在批准前标为草稿。
- 形成问题台账、风险接受记录和 release checklist，等待权利人/公司授权与后续远端验收。

## 明确拒绝或推迟的动作

以下动作在本基线中明确拒绝或推迟：

- 拒绝因为“密码已经删掉”而跳过当前树、Git 历史、tag/branch、Git 对象和 author/committer 元数据扫描。
- 拒绝跳过许可证、版权、第三方依赖、来源和品牌水印授权审查。
- 拒绝在没有公开许可、没有完成 P0 门禁或没有 release 物扫描时创建公开仓库、推送代码、推送 `v1.0.0` tag 或发布 GitHub release。
- 拒绝保留可能属于公司/第三方的 Logo、字体、图片、产品名或水印，除非权利和不背书边界已得到确认。
- 拒绝将本地 build pass、单个 API 200、README 完成或用户口头声明写成安全、合规、公开发布或生产就绪证明。
- 拒绝把内部 CI、私服、环境变量、部署脚本、客户数据、公司邮箱、路径和凭据带入公开仓库。
- 拒绝用强制 reset、无记录批量删除或未审计的历史改写来掩盖发现；若历史含真实凭据，先撤销/轮换，再由授权人员决定重新建公开历史。
- 推迟所有 Git commit/push、GitHub 配置、远端 release、分支保护、远端扫描设置和公开后验证；本次只提供本地治理清单，不访问或改变 GitHub。

在上述门禁有可核验结果并获得必要授权之前，最终建议保持 `PUBLIC_RELEASE_BLOCKED`，而不是发布一个未经审计的 `v1.0.0`。
