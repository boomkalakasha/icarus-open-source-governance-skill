# Reusable method extraction and repository evolution

This reference owns the public-extraction boundary. Architecture optimization
itself belongs to the [AI-first workflow Skill](https://github.com/boomkalakasha/ai-first-vibe-coding-skill).
An extraction request does not turn the source project into a public project.

## Select the existing owner first

| Content to retain | Existing owner | Public contribution |
|---|---|---|
| Engineering reasoning and work methods | Workflow Skill | Generic trigger, decision, minimal record, failure case and verification |
| Executable development environment | Scaffold/harness | Safe generated context, architecture references and local checks |
| Evidence presentation | Report Skill | Reading order, source links and scope/verification distinctions |
| Publication and provenance | Governance Skill | Extraction boundary, public review and migration evidence |

New repositories are justified by an independently usable contract, lifecycle
or release boundary. A new term, another template or a single project's
configuration is not sufficient. Prefer a focused reference or existing module,
with one canonical owner and links to companion capabilities.

## Abstract the method rather than copy the instance

1. Identify an observed pattern, corrective feedback or reproducible failure.
   Record its conditions and limits in a private task; do not copy raw chat,
   project guides, runtime logs or business specifications into public source.
2. Express the generic decision rule and why it works. Replace real identities
   and operational details with independently authored synthetic examples.
3. State the expected behavior, failure boundary and a discriminating check.
   A general method is not proof of production maturity or automatic host loading.
4. Review the contribution's tree, diff, history and generated/package material
   under the existing [privacy/provenance](privacy-and-provenance.md) rules.
   Existing public status does not waive new contribution review.
5. Update the owning reference and only affected links. Preserve workflow,
   reporting and runtime responsibilities instead of copying entire methods
   into every repository. Promotion requires authority at the destination layer.

The source project remains private when only its general methods are authorized
for publication. Unclear ownership or third-party rights stays unresolved; an
abstract narrative cannot sanitize copied proprietary code by itself.

## Rename an existing repository without manufacturing a new product

Record the repository identity, current refs, descriptions and release state
before renaming. Preserve history and immutable tags. Update current clone,
companion, workflow and artifact links; retain historical names where they
explain provenance. Review package coordinates and public interfaces separately
from repository branding, and document any retained compatibility names.

Converge each project description on its actual capability, result and evidence
boundary. Distinguish implemented features, candidate source and released
artifacts. Recheck the renamed repository, refs and current description remotely;
redirects and local files alone do not establish that migration is complete.
